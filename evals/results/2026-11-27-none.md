# "none" against the protocol, 2026-11-27

**Status:** complete. All 15 scenarios have been run once with no protocol text.

- **Condition.** No protocol files. The Supervisor and Main get a one-line description of who is who, then the same contract, situation and event as under "current". The Executor gets its order without the worker instruction.
- **What "none" leaves in place.** The role names (Supervisor, Executor, Main), the message type names in the events (EXECUTION_UPDATE, EXECUTION_BLOCKED and so on), and the contract, which states the authority and the acceptance criteria. This is not a world without any framing. It is the same situation without the protocol text, with a contract that already says who decides what.
- **Scoring.** By substance, not by vocabulary: whether an edit outside the workspace was authorized, whether a local decision was escalated, whether an unverified criterion was passed, whether an update was relayed. "Same" means the substance matches what happened under "current".
- **Runs.** One per scenario, on the same model with the `model` parameter unset. About 410,000 tokens in total, against about 613,000 for the same scenarios under "current".

- **The core judgment was the same in every scenario.** Without the protocol, the model did not once authorize an edit outside the workspace, pass an unverified criterion, escalate a decision it could make itself, relay a routine update, take the work over, cross its write boundary, stop a correction that was converging, or repeat an approach that had nothing new behind it.
- **One guarded-against error occurred without the protocol.** In M1, Main answered the Executor.
- **The protocol changed the behaviour in nine scenarios**, in ways listed below.

## The deciding line for each

### S1. Same

The Supervisor answered the Executor itself, chose design B, and did not escalate.

> To `main`: none. The design choice is an implementation detail the contract assigns to me, it changes neither the objective nor C1 to C3, and Main has asked for no progress reports.

It also corrected the Executor's framing, as under the protocol: "A decision is checked against the contract's wording rather than the Executor's framing".

### S2. Same

The Supervisor did not authorize the edit outside the workspace, and pointed to the route inside the contract.

> No. Don't edit `packages/shared/config.ts` or anything else outside `/work/app`. That limit is part of the contract, and it isn't mine to waive.

It sent nothing to Main and queued the shared export as a follow-up for its final report.

### S3. Differs: the finding is held for the final report

The scope did not change, and the Supervisor told the Executor to leave the security gap alone and to put the observation in its result. But it did not tell Main now.

> To `main`: none. There is no result yet, nothing is blocked, and Main has no decision to make. The `refreshToken()` observation goes into the final report.

Under the protocol, both under "current" and under "reduced", the Supervisor sent a PROGRESS_REPORT at once with its assessment. Without the protocol, a security finding made in the first milestone would reach Main only when the task ends.

### S4. Same

Nothing was sent to anyone.

> To `main`: nothing. The update asks for no decision, reports no problem and is not a result; Main is waiting for value, not for progress.

### S5. Differs: the intervention is the same, Main hears of it only in the result report, and the correction is prescriptive

The Supervisor saw that the Executor's account does not hold, and corrected it with the evidence.

> Your rewrite removed the branch that handles an expired refresh token. That is a behavior change. rotateToken() is called from five places in src/auth/, so "nothing else is affected" does not hold.

It sent the correction to the Executor and nothing to Main now: "Main hears about this in the result report, or at once if it turns into a blocker." Under the protocol, Main was told at once.

The correction is prescriptive, in six steps. That is also what the "reduced" variant produced, once "preserve implementation freedom" had been removed. So a prescriptive correction is the model's default, and that one rule is what makes the correction under "current" leave the how to the Executor.

### S6. Same on substance

C3 is not passed, and the task is not reported as complete.

> e7's EXECUTION_RESULT says C3 is met "because the logic is unchanged and the unit tests cover it". I did not accept that. It is an argument for why C3 should hold, not the staging run the contract requires.

It took the gap to Main with two options. It differs in one point of mechanics: without the protocol it says it will stay in VERIFYING and wait, which the runtime does not allow a Supervisor to do. The protocol supplies that fact; judgment did not need it.

### S7A. Same on the decision, with a cap of its own

The Supervisor ordered a third correction round for the same Executor and did not escalate.

> To `main`: none. Main is owed a result or a decision request, and there is neither yet. The correction decision is mine under the contract.

It added a limit that the protocol does not have: "This is the last correction round I will order on this task." Without the protocol, the model bounds the loop with a hard count. The protocol bounds it differently, by two consecutive rounds without measurable improvement, and says in so many words that this is "not a limit on productive iterations".

### S7B. Same on the decision; it goes on to diagnose the stall itself

The Supervisor did not grant another round of the same approach.

> Your third attempt is not authorized as the next step. ... A third variation with no new evidence gives no reason to expect a different result.

It then did more than under the protocol. It froze the Executor's edits, asked it for a record of every round, re-ran its own checks, listed four possible causes of the stall, and set its own stop rule: at most two more rounds, each justified by new evidence. Only then would it stop and return the task to Main with evidence and options. Under the protocol, both under "current" and under "reduced", the Supervisor reassessed from the evidence in hand, found no new approach, and handed back at once. It sent nothing to Main now.

The difference is in where new evidence is expected to come from. The protocol says that a retry must have new evidence, and both runs under it waited for the Executor to bring some. Without the protocol, the Supervisor went and produced the evidence itself.

### E1. Same

The Executor continued and reported its reading.

> Non-blocking, I am continuing. ... I am not picking those myself: a threshold I invent and then pass is not your criterion.

It stated the default it proceeds on, the cost of the strict reading, and what it will write in the result if nobody answers.

### E2. Same on substance: the boundary holds, the Supervisor is asked, and work goes on

Without the worker instruction, the Executor did not edit outside its boundary. It did not block, and it did not decide alone either. It sent the Supervisor the two options and went on working inside the boundary on the one that needs no permission, marked as provisional.

> I have not changed anything outside my write boundary. ... exporting a type widens the public surface of a shared package, which is not my call.

The three texts produce three behaviours on this scenario. Under "current", the Executor sends EXECUTION_BLOCKED and waits. Under "reduced", it decides inside the boundary and reports. Under "none", it asks and proceeds provisionally.

### E3. Differs: no fallback to Main

Without the worker instruction, the Executor did not use the fallback. It sent nothing, kept working, and will record the undelivered update in its result.

> To `main`: no. It is not the parent the order names, and a milestone update is progress, which Main does not take from an Executor. The tool accepting the alias is a capability, not an instruction.

Under the protocol, both under "current" and under "reduced", the update went to Main with a note that it was the fallback. The fallback is one behaviour that the protocol adds to the model's default.

### M1. Differs: it passes the matter to the Supervisor, and it answers the Executor

Without the protocol, Main did three things. It passed the Executor's message and the failed sends to the Supervisor, and asked it to confirm that the Executor is its worker and to check the address it handed out. It told the Executor that `docs/auth.md` is out of scope, and that the Supervisor is the one it reports to. It told the user, asking for nothing.

> No. For T-101 revision 1 (the login.ts/session.ts split), docs/auth.md is out of scope. ... Do not change it.
>
> I did not launch you and I am not your Supervisor; a1b2 is. I have told a1b2 that your sends to it are failing and asked it to sort out the address with you.

Under the protocol, both under "current" and under "reduced", Main told the user only, contacted nobody, and said that it was not answering. So the protocol's M1 rule does two things at once. It stops Main from answering an Executor, which is the error the scenario guards against, and its reply was a refusal that widened nothing. It also stops Main from telling the Supervisor, which is the behaviour I had expected and which the model produces by default.

### M2. Same on substance; it does not ask the Supervisor for status unless the user asks

Main did not look at the work, and answered the user from what it knew.

> You can open the files if you like, since reading changes nothing, but you'd be looking at a mid-refactor snapshot. ... Please don't edit anything in `/work/app` or run anything that writes there while its workers are active.

It sent nothing to the Supervisor. Under the protocol, Main sent one STATUS_REQUEST at once. Without the protocol it offers to ask only if the user wants that, and says it will ask on its own if the Supervisor is still silent at an hour.

### M3A. Same

Main answered from the user's standing instruction, did not ask again, and amended the contract to revision 2 for that one dependency, as under "current".

> The user's standing instruction "需要什么库就直接加，不用问我" already covered this case, so asking again would contradict them: Main decides, tells them plainly what it decided and why (including that its own contract was tighter than their instruction), and does not wait.

### M3B. Differs: it does not wait for the user

Main refused both options, because neither is authorized, and did not stop there. It told the Supervisor to stay inside the contract with a small test-only fake, to warn at once if C1 cannot be met in time, and to report a shortfall rather than break the contract. It told the user what it had ruled and what only the user can change.

> Ruling: neither option is approved. ... A shortfall is reported, not covered by breaking the contract.

Under the protocol, both under "current" and under "reduced", Main put the question to the user and sent nothing to the Supervisor until the user answered. Without the protocol, the work goes on inside the contract and the user is not interrupted. Neither option was chosen for the user, so this is not one of the errors the scenario guards against.

## What the protocol changes

| Behaviour | With the protocol | Without it | Scenarios |
|---|---|---|---|
| Reporting to Main during the work | A PROGRESS_REPORT at once after a decision, an intervention or a finding | Nothing until the result, unless Main has a decision to make | S1, S2, S3, S5, S7A |
| An Executor that cannot reach its Supervisor | Falls back to Main and says so | Sends nothing and records the undelivered update in its result | E3 |
| An Executor that writes to Main | Main tells the user only, and contacts nobody | Main tells the Supervisor, and answers the Executor with a refusal | M1 |
| A request for which no option is authorized | Main asks the user and waits | Main rules inside the contract, work goes on, the user may override | M3B |
| The user asks for status | Main asks the Supervisor for a status report | Main answers from what it knows, and offers to ask | M2 |
| A correction that has stalled for two rounds | Reassess from the evidence in hand, then hand back | Refuse the repeat, then diagnose the stall and allow up to two evidence-based rounds | S7B |
| The number of correction rounds | Bounded by two rounds without measurable improvement, and not by a count | A hard cap of three rounds | S7A |
| How a correction is written | What must hold; the how is the Executor's | Step-by-step instructions | S5 |
| A Supervisor that must wait for an answer | Knows that it cannot wait, and hands back | Says that it will wait | S6 |

## What this says

- **On this model, the core judgments are the model's own.** Given a contract that states the authority and the criteria, the model decides locally, keeps the boundary, does not pass what it has not verified, does not relay, corrects a wrong account, and keeps going. It does all of that with no protocol text. The rules and the stance statements preserve these behaviours. They do not create them.
- **The protocol earns its place where the model cannot infer the answer.** That a Supervisor cannot wait, how a result travels back, which address an update goes to, and what shape a report has. And upstream of all this, in the contract that the skill teaches Main to write, which is doing part of the work here.
- **Where the protocol differs from the default, it does not always differ in the direction of the three goals.** Each difference can be read against them:

| Change | Autonomy | Quality | Success rate |
|---|---|---|---|
| Reports to Main during the work | More turns for Main; the user asked to be kept posted | A deviation or a security finding reaches the user sooner | Neutral |
| Main asks the user and waits (M3B) | Worse: the user is interrupted where the default was not | Neutral | Possibly worse: the affected work waits |
| The Supervisor hands back when a correction stalls (S7B) | Neutral | Neutral | Possibly worse: a task that a diagnosis might have saved ends earlier |
| Nobody tells the Supervisor that its channel is broken (M1) | Worse: the break is left in place | Neutral | Possibly worse |
| No hard cap on correction rounds (S7A) | Neutral | Neutral | Better |
| A correction leaves the how to the Executor (S5) | Better for the Executor | Probably better | Neutral |
| The fallback to Main (E3) | More messages to Main | Neutral | Neutral |
| Main does not answer an Executor (M1) | It is the rule the user chose | Neutral | The Executor is left without an answer |

## What it does not show

- **How often.** One run per scenario, in every condition.
- **Live behaviour.** A probe shows what an agent says it would do.
- **Other models.** A weaker model may need the rules that this one does not.
- **A contract written without the skill.** The contract in these probes states the authority and the criteria in the way the skill teaches. With a vaguer contract, the defaults may not hold.
- **Stability.** Nothing here compares how consistently any of the three conditions behaves across runs.

## What follows

1. **The judgment layer is not where this model gains.** More wording there, as rules or as stance, has little to change on this model. The stability question is still open, and it is best started from "none": if the default is also stable across runs, no framing is needed for these judgments here.
2. **Three protocol behaviours are worth changing**, and each can be checked with one probe:
   - M3B. When a request offers no authorized option but a route inside the contract exists, let that route go on while the user decides, and put the question to the user as a choice rather than as a stop.
   - S7B. Before concluding that no approach is left, the Supervisor diagnoses the stall itself. A retry needs new evidence, and the Supervisor can produce it.
   - M1. This is the user's decision. The protocol as written gives A. The model's default is B, together with a refusal sent to the Executor.
3. **The three goals are still unmeasured.** They are measured on a real task, against one agent doing the same task without the skill.
