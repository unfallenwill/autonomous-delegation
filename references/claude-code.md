# Claude Code runtime adapter

Use the tools and parameter schemas actually available in the current session. This document maps protocol intent onto Claude Code; it cannot add runtime capabilities or enforce tool permissions.

## Launch and ownership

- Main uses the Agent tool with a general-purpose or other Agent-capable subagent, and leaves it unnamed. Keep the agent ID from the launch response as the Supervisor's address and send it to the Supervisor as one SUPERVISOR_ADDRESS message right after launch: an unnamed agent is not told its own address and cannot look it up, and its Executors report to it through that ID. Maintainer note: a named Supervisor would be safe only in a version in which a named agent waiting on a nested call still receives its children's reports; the build tested here does not. In interactive sessions a subagent spawned from the main conversation starts in the background; if the schema exposes an explicit background control, use it. Provide explicit role, contract, paths and parent routing. Do not use Explore/Plan for Supervisor. Avoid context: fork on the Skill itself: Main must author the contract in its own conversation.
- Supervisor must have Agent access and sufficient nesting depth (at least two child layers below Main; Claude Code allows three by default, controlled by `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`). Confirm its capability on entry; if not available, return BLOCKED. Do not change settings or permissions automatically.
- Prefer whichever nested call keeps the child's report with the Supervisor and leaves the Supervisor able to report to Main. Where the call blocks until the child ends, nothing can be sent or read until it returns, so size execution orders so that each return is a natural checkpoint. Where it returns at once with the child in the background, the report arrives later as a handback message; retain ownership until it arrives and never intentionally finish while a child is still active. A subagent Supervisor cannot idle until then: if it ends its turn with a child still active, the runtime forces it to hand back to Main. Keep working in bounded steps, such as preparing or running checks, until the child's handback or its result at the result location arrives. When no useful step is left, wait with a bounded read-only check of the result location and repeat it while the child is active; that is not polling the Executor. In noninteractive/SDK modes, nested background results can escape to Main if Supervisor exits; prefer a supported foreground child or report incompatibility when ownership cannot be preserved.
- Launch Executors unnamed as well. A named Executor behaves as a teammate that reports to Main instead of handing its report back to the Supervisor, and a named Supervisor cannot spawn named agents at all.

## Transport modes

**Live messaging:** If SendMessage or an equivalent native channel is exposed, address the verified parent/child by actual ID, unambiguous name or the runtime's parent alias such as `main`. Use only supported fields. An Executor sends to its Supervisor at the parent address in its order; the Supervisor sends its reports to Main. An Executor messages Main only when it cannot reach the Supervisor. Named agents and routing are runtime capabilities, not arbitrary string conventions. In the Claude Code build tested, an unnamed Supervisor is neither told its own address nor able to list agents, and an Executor given no address cannot find its parent and may reach an unrelated agent by guessing. That is why Main sends the Supervisor its agent ID as a SUPERVISOR_ADDRESS message right after launch and every EXECUTION_ORDER carries it as the parent address. With that address, an Executor's message is delivered to the Supervisor at its next tool round, within seconds while the Supervisor is active. A message to Main is queued for Main's next turn and does not pass through the Supervisor. Send the events the communication protocol requires. Do not use team-only structured messages unless the runtime supports them. A successful send is not a decision response.

**Child results:** An Executor's final report reaches the Supervisor only through the runtime's handback, and a run can lose it: the launch response may say the child ended without delivering a report, or the report may surface to Main instead. Treat either as neither success, failure nor an empty result. Every EXECUTION_ORDER therefore names a result location, and the Executor writes its EXECUTION_RESULT there before it ends. If the handback is missing, read the result from that location; if it is not there, message the child by ID to ask for its report; if neither works, report UNKNOWN. The handback reaches an unnamed Supervisor at its next tool round, or resumes it if it has already ended its turn; after such a resume a second handback is refused, so the terminal report then goes to Main by SendMessage.

**Handback:** The terminal report is delivered as the Supervisor's handback. When a live channel exists, the Supervisor ends its run with the report and does not also send it by SendMessage; it sends the report by SendMessage instead only when its handback will not be delivered, for example after the runtime resumed it following an earlier handback, and Main treats a second copy as a duplicate. If live messaging is absent or fails, everything due to Main travels in the handback, and intermediate progress and decision requests may be delayed until then. A delivered child result is the Supervisor's feedback channel. Do not fake asynchronous delivery with a text response, invent a wait/poll tool, or ask Main to continuously poll. If the task needs a live decision, stop affected work and return BLOCKED with a complete decision request and recovery identity. If a running child cannot be safely stopped or reconciled, report UNKNOWN rather than claiming a clean handback.

## Resume, status and cancellation

Use actual agent IDs from tool responses. Where supported, SendMessage to a completed agent resumes its context; otherwise use an exposed resume mechanism. Reuse the same Supervisor for decisions and recovery. Runtime user cancellation may prevent auto-resume: respect that. Never read arbitrary private transcripts to recover state when normal runtime controls or authorized task state suffice. For cancellation, propagate CANCEL to Supervisor; use the native stop facility for known running descendants if needed and permitted, confirm their states, and report any remaining processes. Tool or permission prompts can still interrupt Main; the protocol cannot suppress them.
